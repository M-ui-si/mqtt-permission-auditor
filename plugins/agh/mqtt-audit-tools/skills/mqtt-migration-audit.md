---
name: mqtt-migration-audit
description: Plan and run the fixed local Mosquitto to EMQX ACL migration acceptance check when the user states only the audit goal; report evidence and unknowns.
---

Use this skill when the user's goal is to accept or investigate a Mosquitto → EMQX file ACL migration on the project's isolated local instance. The user may state only the goal; choose the steps yourself. Do not require the user to dictate tool order.

1. Find the `mqtt_audit_*` tools available in the current AGH session. Call `mqtt_audit_list_cases` to learn the fixed case set and expectations. If the tools are unavailable, state that the plugin is not available in this session; do not invent a run.
2. For the local migration acceptance goal, first call `mqtt_audit_prepare_run` with `caseId="migration-baseline"` and `instanceId="local-isolated"`, then call `mqtt_audit_run_check` with the same selection and returned `runId`. Preparation does not connect to a Broker. The initial acceptance run must cover all c1–c8. These are the only supported identifiers. Do not use arbitrary paths, hosts, credentials, shell commands, or external targets.
3. Examine the structured response. If it is an error, name the error and the missing local prerequisite. Do not treat an error, timeout, broker outage, or missing evidence as an ACL denial or a passing audit. After the prerequisite is restored, run the fixed check again if possible.
4. If the result is truncated or details need checking, call `mqtt_audit_read_result` with the `runId` returned by `run_check`. Use the structured result as the source of truth, not a prose guess or a stale dashboard view.
5. Report three separate dimensions: permission expansion, business damage, and independent business-requirement compliance. Include the overall pass/fail/unknown state, concrete check IDs, source/target observations, and evidence limits. Keep every `unknown` as unable to determine. A target-side forbidden delivery can establish a requirement failure even when the source side is unknown; it does not by itself establish expansion.
6. If the user asks for a remedy, explain a candidate ACL rule-order change and the checks needed to verify it. Do not change Broker configuration unless explicitly requested. Request a retest only after an actual condition changes (configuration correction or observed environment recovery). Prepare it with `parentRunId` and selected `checkIds`, then execute the returned runId. At most two retest rounds per root task; clearly label partial coverage and compare matching check IDs. A repeated protocol limitation alone does not justify another retry.
7. Optionally call `mqtt_audit_plan_next({runId})` for a Jev recommendation when backend configuration enables it. It receives only bounded synthetic observations and uses a fixed provider/model; it cannot execute tools or decide permissions. Default is Agnes-only. An unavailable suggestion is nonfatal: continue planning yourself. Limit three requests per root task. State the actual suggestion separately from your chosen action and explain why they differ. Do not claim an unavailable recommendation was used. Competition demonstrations remain Agnes-only until external rules permit Jev.

This workflow uses AGH's own tool calls and feedback. Never substitute a simulation or claim full ACL equivalence from the finite case set.
